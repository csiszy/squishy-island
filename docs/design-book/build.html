For the builder · build plan

How the real game gets built

The game is built in Godot 4 for Android first, with a small Nakama game server in the EU. The 3D models, sounds and numbers come straight out of this design book, so the book stays the single source of truth. Every minigame is a sealed folder that only talks to the game through one small, versioned contract, so any minigame can be changed, replaced or switched off without touching anything else.

  • Engine: Godot 4.6 (free, open source)
  • Language: typed GDScript
  • Server: Nakama + PostgreSQL on an EU server
  • Store: Google Play first
  • Running cost: about €5–15 a month at launch

Engine choice

Why Godot (and not Unity after all)

Why it fits this project

  • Free with no strings: MIT licence, no fees, no revenue limits, no account or licence activation to build.
  • Everything is a text file: scenes, materials, themes and scripts are all readable text. I can write, review and test every part of the game in code, and every change shows up clearly in version history.
  • Builds from the command line: tests and Android builds run automatically on every change, without anyone clicking through an editor.
  • Small download size, quick start-up, good 2D tools for the minigames and UI, and enough 3D for the soft toon look of the city.

The trade-offs, and how we handle them

  • Fewer ready-made store plugins than Unity. Billing and ads sit behind our own small interfaces. We use the existing Godot plugins where they are up to date, and otherwise write a thin Kotlin plugin of a few hundred lines ourselves.
  • Older and cheaper phones: Godot’s Mobile renderer, with the Compatibility renderer (OpenGL ES 3) as a fallback, plus the Low graphics tier.
  • Fewer Godot developers to hire than Unity developers. Clear structure, tests and this book make the project easy to hand over.
  • The earlier Unity recommendation on the Testing Facility page is replaced by this plan. The physics advice there still applies, in GDScript instead of C#.

The minigame wall

The minigame host (a feature) is the only thing that touches a minigame, and only through the contract in minigame_api/:

Minigames can’t see coins, saves, ads, billing, the server, other minigames or each other’s files. They play, then report a Result.

Rules that keep it modular

  • Dependencies only point down. Features never use other features directly; they talk through Events (“box_opened”, “house_upgraded”) and core services.
  • No hard-coded numbers in code. Prices, odds, coin rules, level costs and quest targets live in data files, and the server can override them without an app update.
  • Every outside service has a fake. Billing, ads, server and haptics all have a pretend version, so the whole game runs on a computer and in tests with no phone, no store and no internet.
  • Save files have a version number and a migration step for every change, so an update never breaks an old town.
  • An automatic check on every change enforces the rules (see “Guard rails” below), so they can’t slowly erode.

What lives where

  • On the server (it decides): Gems, purchases, box rolls, the Spare Shelf, trades, quests, the Gem Challenge target, the weekly visitor, account linking and deletion.
  • On the phone, checked by the server: coins earned in minigames. The server refuses impossible amounts (more than about 60 coins per minute of reported play).
  • Only on the phone: settings, best scores, minigame level progress (backed up with the cloud save).
  • Offline: the map and all minigames work. Boxes, trades, Gems and quests need a connection and say so kindly.

The minigame contract

How a minigame plugs in

A minigame is a folder. The game finds every minigames/*/manifest.json at start-up, so adding, removing or replacing a game never means editing anything outside its folder. The host handles everything around the gameplay; the game handles only the gameplay.

manifest.json (comments only explain it here)

{
  "id": "sky_bounce",              // = the folder name
  "api": 1,                        // contract version it was built for
  "version": "1.0.0",
  "title": "sky_bounce.title",     // words: keys in the game's own strings_en.csv
  "building": "playground",
  "kind": "endless",               // endless | levels | songs | toy
  "scene": "sky_bounce.tscn",
  "music": "sky",                  // a track of the sound pack
  "size": [360, 640],              // the game's own drawing space
  "backdrop": "#8CCBFF",           // colour around it on taller phones
  "how_to": ["sky_bounce.how.1", "…"],
  "coins": { "from": "metric",     // score | metric (coins grabbed)
             "divide": 1,
             "milestones": [600, 1200, 2000],
             "unit": "sky_bounce.unit" },
  "goal": "score",                 // what counts for the building's level goal
  "revive": { "allowed": true,
              "gift": "sky_bounce.revive_gift" },
  "perks": [{ "family": "sky", "effect": "fall_slower", "amount": 0.25 }],
  "enabled": true                  // the server can switch it off
}

The contract (minigame_api v1)

# what every minigame extends (game/minigame_api/)
class_name Minigame extends Node2D   # draws in its "size"; the host scales it

signal finished(result: MinigameResult)
signal score_changed(score: int)

func setup(ctx: MinigameContext) -> void: pass
func start(level: int = 0) -> void: pass
func pause() -> void: pass
func resume() -> void: pass
func stop() -> void: pass          # player left: end the run now
func can_revive() -> bool: return false
func revive() -> void: pass
func advance(delta: float) -> void: pass  # all game time

# MinigameContext: the ONLY things a game can use
#   squad            squishies the player brought (pictures: portrait(id))
#   perks            helper effects the squad switches on
#   settings         vibration, quality tier, reduced motion, left-handed
#   sfx(id) play(sound) buzz(ms) rng(seed) font(kind) t(key)
#   store            this game's own little save box
#   best             the player's best score so far
#   request_revive() asks the host (the host shows the ad)

# MinigameResult: what it gives back
#   score, metric, won, level, stars, seconds_played

# minigame_kit/v1: KitGame = the prototypes' engine in Godot
#   (drawing helpers, taps, floating text, tones, "keep going?")

The host does, so games never have to

  • The start card (title, how to play, best score, levels or tracks) from the manifest.
  • Pause (button and the phone's back button), sound and music switches, leaving: “Finish here” ends the run and still pays for what was reached.
  • Which squishy plays (the player picks one they own); its family’s helpers and Cozy bonus.
  • “Keep going?” with the ad (closable after 5 s); then calls revive().
  • The results screen with the half-second count-up, coins from the manifest’s coin rule, milestone bonus, best score, “back to town” during the tour.
  • Music from the manifest, ducking, the graphics tier, squishy perks.
  • Sending the run to the server and paying out.

So re-balancing coins, changing the ad rules or restyling the results screen never touches a minigame.

Why a broken game can’t break the rest

  • Boundary check: a script fails the build if a minigame loads any file outside its own folder, minigame_api/ or minigame_kit/v1/.
  • Frozen helpers: minigame_kit/v1 only gets bug fixes. New helpers go into v2, so a game that works today keeps working.
  • Own save box: each game saves only under its own name; it can’t touch coins or other games’ data.
  • Contract test: on every change, every minigame is started headless and played by its bot (or random taps) for two minutes. The test fails on any error, a missing Result, a score that goes backwards or leaking memory.
  • Safe host: if a game doesn’t start within 5 seconds or reports an error, the host closes it, says “This game is taking a nap, try another!” and logs it.
  • Off switch: the server can disable a single game version for everyone, without an update.

Changing, adding or removing a minigame

  • Change one: edit only its folder, run its harness.tscn on a computer (it fakes the host, like today’s prototypes), and its bot and contract test confirm nothing broke. Bump its version.
  • Add one: copy _template, fill in the manifest (which building it belongs to), write the gameplay. It appears in the game automatically.
  • Remove one: delete the folder, or set "enabled": false. Its building simply shows “coming soon”.
  • Port from the prototypes: each game in play/ already follows this shape (the host-side parts live in its shared engine), so porting is mostly translating its game file.

Pipelines

From the design book into the game

WhatHow
3D modelsA script opens the design book in a headless browser, builds every building at every level (and the Gem Mine), every squishy, the decor and the room sets, and saves each as a glTF file (building_dumpling_L07.glb, squishy_bao.glb). The squishies’ idle animations travel along as tags, and Godot’s import script turns them into a small reusable “idle” component.
LookOne toon shader and one outline shader in Godot reproduce the book’s look. The import script swaps every material for them, so changing the look later is one file. The shader does the book’s lighting sum (hemisphere + ambient + sun through the 4-step ramp) on sRGB colours like the book does, so a building in the game looks like its picture here.
PicturesSquishy portraits, icons and badges rendered to PNG from the same scripts.
Numbers and textSquishies (names, bios, rarities), buildings, level costs, decor, odds, prices, quests, the city layout (the CITY block), story and tutorial lines: exported to JSON, with all player-facing text in strings_en.csv from day one, so adding a language later is just translation. Box, collection, Gem, ad and unlock numbers have one machine-readable home in this book, art/economy.js (the guide explains them in words; change both together). Words the game needs that are on no page yet (buttons, messages) live in docs/strings_ui_en.csv. The export checks that the book agrees with itself (odds add up to 100, decor design prices, Gem prices) and CI fails if game/data falls behind the book.
SoundThe rendered pack. Squeak Beat: each song becomes a backing track plus a note chart and one melody note per pitch, so taps still play the tune with no lag from live synthesis.
Replacing with hand-made artDrop a file with the same name into art/overrides/. Nothing else changes.

Quality

Speed, tests and safety nets

Speed targets

  • 60 fps on mid-range phones, steady 30 fps on Low; start-up to the map under 6 s.
  • Download under 150 MB; memory under 400 MB on a 3 GB phone.
  • The map: buildings far from the camera use simpler versions; squishies idle only when near; shadows by tier (see graphics tiers).
  • Auto graphics tier: phone memory and cores, plus a 3-second check during the story, as specified in Settings.
  • Squeak Beat gets a tap-timing calibration screen, because audio delay differs between Android phones.

Tests

  • Unit tests for the economy, box odds and pity, Spare Shelf levels, quests, save migrations.
  • Contract tests for every minigame (above), and balance tests: bots play each game and check the coins per minute stay near 35.
  • Server tests: purchases can’t be granted twice, refunds take Gems back, impossible coin amounts are refused, trades can’t duplicate squishies.
  • Screenshot tests of key screens on small and large phones.
  • Real phones: your phone plus one cheap Android, through Google Play’s internal testing track, then the 12-tester closed test.

Roadmap

The order I’d build it in

Each step ends with an installable build on your phone through Google Play’s internal testing track. Weeks are rough estimates for me writing the code with you testing and deciding as we go.

Step 0~2 weeks

Foundations

  • Repository, Godot project, automatic tests and Android builds.
  • Core services with fakes: save, settings, audio, haptics, events, text.
  • The three export tools (art, data, sound) and the toon look.
Step 1~4 weeks

The town

  • City map from the CITY layout: drag, pinch, bubbles, building cards.
  • Houses: renovating, rooms and decor; squishies idling around town.
  • Factory boxes, Spare Shelf and collection book (with a pretend server).
Step 2~3 weeks

Minigame host + first 3 games

  • The contract, host, results screen, payout, template, boundary check, contract tests.
  • Port Sky Bounce, Bistro Rush and Sort-a-Lot. The core loop is now playable end to end.
Step 3~5 weeks

The other minigames

  • Style Studio, Grow Grow Garden, Lost & Found, Bucket Brigade, Squish Breaker.
  • Squeak Beat (songs, charts, calibration) and the Squish Lab (soft body with the 3D squishy).
  • These can be built in any order, one at a time, because they’re independent.
Step 4~4 weeks

Server

  • Nakama on an EU server: guest accounts, cloud save, “save my town” codes, transfer codes, deletion.
  • Server-side boxes, coins checks, quests, Gem Challenge, the weekly visitor, the Market and trading.
Step 5~3 weeks

Gems, ads and grown-ups

  • Gem Mine with Google Play Billing (tested with Google’s test cards), Gem Shop, refunds.
  • Rewarded ads (keep going, free boxes) with the kids’ settings.
  • Grown-up gate, spending limit, purchases and ads switches.
Step 6~3 weeks

First five minutes and polish

  • Opening story, name picking, the first tour, the i help topics.
  • Settings screen, graphics tiers, battery saver, accessibility, every sound in place.
Step 7~4 weeks

Launch

  • Privacy policy, terms, Data safety, ratings (see Legal), store page.
  • Closed test: 12+ testers for 14 days, kid playtests, fixes.
  • Soft launch in a few EU countries, check the numbers, then wider release.

Total: roughly 7 months to a public release. Steps 3 and 4 can overlap, and a smaller first version (fewer minigames at launch, the rest added in updates) could launch about two months sooner.

Working together

Who does what

Me

  • Write the game, server, tools and tests in the repository, as small reviewable changes with a plain-language summary each time.
  • Keep this design book in step with the game: when a rule changes, the page changes in the same piece of work.
  • Run the bots and balance checks and report the numbers.

You

  • Accounts in your name: Google Play Console, GitHub, the server host, a domain. Keep the app-signing key with Google (Play App Signing) so it can’t be lost.
  • Play every build on your phone (and a cheap Android), and say what feels wrong. Find kid playtesters and the 12 closed testers.
  • The decisions: the final name, prices, which minigames are in the first release, and the lawyer review.

Biggest risks and what we do about them

  • Store plugins lag behind Google’s requirements: keep them behind our interfaces and own a thin Kotlin plugin if needed.
  • The 3D city is too heavy for cheap phones: test on a cheap phone from Step 1, simpler far-away buildings, Low tier.
  • Rules change (EU Digital Fairness Act): Gems, ads, boxes and trading each sit behind a server switch and remote config.
  • Server trouble: nightly off-site backups, uptime alerts, and the game still plays offline.
  • Scope creep: launch with the core loop and a few minigames, then add the rest; the sealed minigames make updates low-risk.
